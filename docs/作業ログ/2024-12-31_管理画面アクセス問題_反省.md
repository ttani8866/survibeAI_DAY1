# 管理画面アクセス問題 - 反省と改善

## 発生日時
2024年12月31日（約4時間）

---

## 1. 問題の概要

管理者が `/admin` にアクセスしても403エラーが表示され続けた。

---

## 2. 根本原因（真因）

### 原因1: MongoDB Atlas のIPアクセスリスト未設定
- Vercelからのアクセスが許可されていなかった
- `0.0.0.0/0` を追加する必要があった

### 原因2: JWT callbackのロジック不備
```javascript
// 問題のあったコード
if (dbUser) {
  token.role = isAdmin ? "admin" : "user";  // DBアクセス成功時のみ設定
}

// 修正後のコード
token.role = isAdmin ? "admin" : "user";  // DB接続に関わらず必ず設定
```

### 原因3: Google Workspaceの組織ポリシー
- 会社のGoogleアカウントはOAuth制限でブロックされていた
- 個人Gmailを使う必要があった

---

## 3. なぜ4時間もかかったか（反省）

### 3.1 場当たり的な対応
- エラーが出るたびに「とりあえず試す」を繰り返した
- 根本原因を特定せずに修正を重ねた

### 3.2 コードの事前確認不足
- 認証フローのコードを最初に確認すべきだった
- 設計書との整合性を確認すべきだった

### 3.3 環境差異の把握不足
- ローカルと本番（Vercel）の環境差異を考慮していなかった
- MongoDBのネットワーク設定を確認していなかった

### 3.4 不明瞭な指示
- 「シークレットモードで試してください」など曖昧な指示を繰り返した
- 手順を最初から最後まで明確に示さなかった

## 4. こうするべきだった（正しいアプローチ）

### ステップ1: 問題の切り分け
1. Vercelのランタイムログを確認
2. エラーメッセージを特定
3. 認証フローのどこで失敗しているか特定

1. `src/app/api/auth/[...nextauth]/route.ts` を読む
2. signIn, jwt, session 各callbackの処理を追う

### ステップ3: 環境の確認

3. Google Cloud ConsoleのOAuth設定を確認

### ステップ4: 修正と検証
1. 修正箇所を特定
2. 修正を実施

## 7. 教訓

1. **「動かない」の原因は必ずある** - 推測ではなく調査で特定する
2. **環境の違いを意識する** - ローカルで動いても本番で動くとは限らない
3. **設計書と実装の整合性** - 設計書があるなら、まずそれと照らし合わせる
4. **明確な手順を示す** - 「試してください」ではなく、1から10まで具体的に
5. **最初に全体を把握する** - 部分的な修正の前に全体像を理解する
